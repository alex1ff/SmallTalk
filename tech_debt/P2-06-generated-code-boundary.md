# P2-06 — явная граница бывшего FlutterFlow-кода

**Приоритет:** P2 · **Размер:** L/XL · **Зависимости:** P2-02, P2-03
**Цель:** сделать ownership и правила изменений понятными, сохранив рабочий
экспорт и не устраивая массовый перенос файлов.

## Почему это долг

В `lib/flutter_flow` и feature-папках смешаны generated-style records,
ручные страницы и бизнес-логика. Есть около 44 `ignore`/`ignore_for_file` и
крупные файлы по 4–6 тысяч строк. README уже описывает экспорт как больше не
генерируемый, но граница не закреплена: новый код легко добавить не туда, а
будущая генерация может затереть ручную правку.

## Минимальный план

1. Зафиксировать ownership в `CONTRIBUTING.md` и коротких README: что считается
   generated/legacy, что можно менять, где должны жить domain/service/repository
   изменения.
2. Для новых изменений использовать hand-maintained feature/services; не
   добавлять бизнес-правила в `lib/flutter_flow` и огромные widget-файлы.
3. При касании legacy-файла выделять только ближайшую чистую seam (модель,
   service или controller), сохраняя публичные импорты и поведение.
4. Пометить реально generated records заголовком/комментарием и составить
   список кандидатов на удаление только после поиска импортов и runtime-проверки.

## TDD/проверки

- Characterization tests до выделения seam.
- Architecture check/grep в CI: новые прямые Firebase-вызовы в widgets и новые
  `ignore` требуют явного исключения.
- После каждого выделения — `flutter analyze`, feature tests и smoke flow.

## Подводные камни

- Нельзя удалять файл только по имени `generated`: его могут импортировать
  маршруты, records или FlutterFlow helpers.
- Не менять сериализацию существующих records без миграции данных.
- Следить за циклическими импортами и увеличением rebuild scope.
- Комментарий «generated» не должен запрещать необходимый bugfix; он должен
  направлять место для следующего кода.

## Не делать

Не переименовывать и не переносить сотни файлов, не менять state-management
framework и не генерировать новый слой абстракций без конкретного consumer.

## Готово, когда

- правила ownership доступны команде и проверяются в PR;
- новые бизнес-изменения идут через узкие services/controllers;
- список generated/legacy подтверждён импортами;
- размер и ответственность критических компонентов уменьшаются только там,
  где это окупается тестами и безопасностью.

## Риск, abort и откат

- **Abort:** обнаружен скрытый импорт/regen path, цикл или behavior regression;
  boundary change остановить.
- **Откат:** revert ownership/header/extraction commit; generated records и
  публичные imports вернуть прежними.
- **Необратимость:** отсутствует, пока файлы не удаляются; deletion только в
  отдельной задаче с inventory/backup.
