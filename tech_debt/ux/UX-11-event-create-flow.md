## Объём задачи и критерии приёмки

Приоритет: средний; пользователь допускает реальную серверную задержку, если
её нельзя безопасно сократить. Фото 5–6 показывают ожидание кнопки, затем деталей.

Подтверждено: `_submit` в `event_create_widget.dart` ждёт `createEvent`, очищает
кэш списка и переходит по `eventId`; детали загружаются отдельно. Backend уже
атомарно записывает `events_public` через `writeEventPreview` в transaction.
Не следует автоматически списывать задержку на ожидание projection trigger.

- Измерить отдельно submit/callable и загрузку после перехода. Дать кнопке
  немедленное понятное состояние «Создаём…» / «Creating…» вместо одного спиннера,
  сохранив размеры и введённые поля.
- После подтверждения создания передать разрешённый initial event/preview на
  экран из 09. Предпочесть нормализованные данные из server response, при нужном
  расширении ответа соблюдать совместимость со старым клиентом. Данные формы
  допустимы как временное представление, но не как подтверждённые серверные права.
- Вставить подтверждённое событие в подходящие кэши списка/«Мои события»,
  учитывая локацию, дату и фильтры. Не сбрасывать все списки в cold loading.
- Сохранить существующий `createRequestId` и защиту от повторов. Timeout после
  фактической записи не должен создавать дубликат при retry. Не показывать
  «Событие создано» и не уходить с формы до подтверждения сервера.
- Если оставшаяся задержка необходима, сохранить честное ожидание с рабочей
  обработкой ошибок. Не вводить сложную offline-очередь создания ради анимации.

Приёмка: двойное нажатие и retry после неоднозначного ответа дают одно событие;
форма сохраняется при ошибке; после успешного создания основной контент деталей
появляется без нового пустого loading screen. Измерения до/после приложить к задаче.

## Результат выполнения

Причина подтверждена: submit показывал только spinner, после ответа сбрасывал весь
кэш списка и переходил в detail только с `eventId`, вызывая второй пустой экран.

Выполнено:

- submit сохраняет размер и показывает «Создаём…» / `Creating…` рядом с
  индикатором; повторное нажатие по-прежнему заблокировано;
- после подтверждённого `createEvent` в detail передаётся безопасное публичное
  preview из нормализованных полей формы; точное место и действия не открываются
  до ответа detail backend;
- matching-кэши списка и уже загруженной истории получают созданное событие без
  общего cold reset; учитываются user, city, date range и level filter;
- exact location добавляется только в приватную историю владельца, не в публичный
  list/detail preview;
- `createRequestId`, retry и защита от двойного submit сохранены; успешный ответ
  после ухода с формы трекается и обновляет нужный cache, но не навигирует.

Проверки до review loop:

- совместный прогон `event_create_widget_test.dart`,
  `event_history_widget_test.dart`, `event_list_widget_test.dart` — 317/317;
- `flutter analyze --no-pub` — без замечаний;
- `git diff --check` — без замечаний.

Review loop (2 прохода):

- проход 1 — 7/10, test quality 6/10; исправлены поздняя перезапись seed
  фоновым refresh и обрезка Unicode-графем;
- проход 2 — 8/10, test quality 8/10; единственное замечание касалось отсутствия
  воспроизводимых физических timing-замеров;
- после исправлений 402/402 теста и analyzer прошли повторно.

Ограничение измерений: числовой baseline до изменения не снимался, поэтому
ретроспективные значения не заявляются. Автоматически подтверждено, что preview
виден до завершения detail stream и поздний refresh не стирает созданное событие.
Замеры `tap → callable → preview → confirmed detail` на физическом устройстве
явно перенесены в [UX-14](UX-14-verification-and-release.md); это не блокирует
готовность кода UX-11, но блокирует заявление об измеренном ускорении на устройстве.

Commit/deploy и проверка на физическом устройстве пока не выполнялись.
