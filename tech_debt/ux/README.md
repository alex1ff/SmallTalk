## Общие правила

- Исследование, ограничения выводов и источники: [UX_STABLE_LISTS_PLAN.md](../UX_STABLE_LISTS_PLAN.md).
  Подробные требования каждой задачи живут в её task-файле; исходный документ
  остаётся справочным исследованием, а не второй копией очереди.
- В начале задачи сверить актуальный код и git diff. Указанные в исследовании
  строки относятся к исходному commit и могли сдвинуться.
- Минимальные исправления по подтверждённой причине, без смены SDK, массового
  рефакторинга или новой БД только ради этих дефектов.
- После Flutter-изменений: `flutter analyze` и релевантные существующие
  `flutter test`. После backend-изменений: ESLint и профильные tests;
  после изменения Rules — emulator checks. Для правки только документации
  достаточно проверки целостности документа и ссылок.
- Новые тесты — на реальное поведение и риски: async races, доступ, повторы,
  неизвестное состояние и геометрию. Не писать тесты, повторяющие реализацию.
  Успешные проверки не повторять без новых изменений или обнаруженных рисков.
- После каждой реализованной задачи — `loop-code-review`; исправить подтверждённые
  замечания и выполнить затронутые проверки. Обновить статус в task-файле и индексе.
- UI-кэш не разрешает платные/приватные действия. Сохранять account isolation,
  серверные проверки, идемпотентность и защиту от устаревших ответов.
- Backfill/repair сначала подготовить и проверить в dry-run. Подготовку скрипта
  не считать выполненной production-миграцией; результат запуска фиксировать отдельно.
- Физические проверки выполняет пользователь в финале; отсутствие device QA
  указывать явно. Кодовая готовность не равна подтверждённой готовности к публикации.
- Перед выпуском выполнить local release gate, указать commit, состав deploy и
  результаты. Создание этих task-файлов само по себе не запускает реализацию,
  commit/push, backfill или deploy.

## Ведение результата

Статусы: TODO → IN PROGRESS → CODE DONE → DONE. BLOCKED использовать с конкретной
причиной и следующим действием. CODE DONE означает, что код и локальные проверки
готовы, но осталась обязательная проверка, миграция или device QA.

В разделе «Результат выполнения» записывать изменённые файлы/commit, команды и
результаты проверок, verdict review, миграции/deploy (если требуются) и ограничения.
В UX-14 собрать итоговую матрицу приёмки; не отмечать непроведённые проверки зелёными.
