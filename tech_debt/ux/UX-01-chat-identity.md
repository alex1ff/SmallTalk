## Объём задачи и критерии приёмки

Приоритет: высокий. Эффект: строка сразу выглядит как известный диалог.

- Сохранять в диалоге минимальный server-owned snapshot участников:
  `participantInfoByUserId[uid] = {displayName, photoUrl}`. Использовать только
  публичные поля, не копировать email, телефон и приватные данные пользователя.
- Покрыть все пути создания/восстановления диалога через `buildConversationSeed`
  и обновление существующего документа, где snapshot отсутствует. Чтения внутри
  Firestore transaction выполнить до записей; новые lookup не должны ломать
  открытие чата, если публичный профиль отсутствует.
- Для старых диалогов подготовить отдельный ограниченный, повторяемый backfill:
  dry-run, страницы, только недостающие поля; не изменять read markers, порядок
  inbox, `updatedAt`/`lastMessageAt`, права или историю сообщений.
- На клиенте брать имя из уже известного актуального профиля, иначе из snapshot
  диалога; догружать профиль без сброса хорошего имени в fallback.
- Объединить разрозненные lookup профиля списка/переписки в небольшой общий
  user-scoped кэш с синхронным чтением и single-flight. По возможности расширить
  существующий `UserPublicProfilePreloadRepository`, не создавать ещё один кэш.
- Недостающие профили загружать пакетами для видимых строк, не ждать самый
  медленный профиль, чтобы показать весь inbox. Для legacy cache miss оставить
  место под имя без временной надписи «Собеседник» и буквы «С»; ошибка или
  подтверждённое отсутствие профиля должны иметь конечное нейтральное состояние.
- Учесть переименование, явное удаление аватара, удаление профиля. Пустой `photoUrl`
  в свежем подтверждённом профиле не должен восстанавливать старый снимок аватара.
  Snapshot диалога — fallback; политика его обновления/очистки должна быть явной.
  Массовый fan-out на каждый просмотр профиля не нужен.

Файлы: `lib/students_pages/favorite/favorite_widget.dart`,
`lib/services/user_public_profile_preload_repository.dart`,
`firebase/custom_cloud_functions/chats_shared.js`,
`firebase/custom_cloud_functions/conversation_unlock_events.js` и другие callers
`buildConversationSeed`, найденные перед реализацией.

Приёмка: новое имя отображается с первого кадра при наличии snapshot/кэша;
повторный вход не показывает fallback; медленная сеть не меняет имя на заглушку;
смена аккаунта не показывает профиль/строки предыдущего пользователя.
Проверить backend seed/backfill и widget-сценарии с задержанным profile loader.

## Результат выполнения

- Подтверждена причина: каждая строка начинала отдельный запрос публичного профиля,
  а `participantInfoByUserId` отсутствовал в серверном seed диалога; до ответа UI
  показывал «Собеседник» и временную букву.
- Все серверные пути создания/восстановления диалога, включая чат организатора
  события, теперь сохраняют
  `participantInfoByUserId` только для участников и только из `displayName`/
  `photoUrl`. Email и иные поля не копируются; явное удаление аватара сохраняется
  как `null`, старые хорошие имена не стираются пустым значением.
- Inbox заранее запускает один batch максимум для первых 30 диалогов; row futures
  присоединяются к single-flight TTL-кэшу. Завершённый Future больше не удерживает
  профиль навсегда, кэш очищается при смене аккаунта. Snapshot
  виден на первом кадре, актуальный профиль затем может бесшовно его заменить.
- Если актуальный профиль подтвердил пустой `photoUrl`, устаревший avatar snapshot
  больше не восстанавливается ни в inbox, ни в заголовке переписки.
- Добавлен `backfill:conversation-participant-info`: страницы по 50 документов,
  не более 20 страниц за запуск, dry-run по умолчанию, `--apply` для записи и

  конфликт не затирает параллельное изменение. Добавляются только недостающие
