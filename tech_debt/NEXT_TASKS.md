## Общие правила выполнения

- Один пункт выполнять небольшими проверяемыми срезами. Не объединять
  обновление SDK, изменение схемы данных и оптимизацию экрана в одну правку.
- Для исправления бага сначала воспроизвести его или зафиксировать нарушаемый
  контракт. Добавлять тесты на реальные риски, не на количество строк кода.
- После изменения Flutter-кода: `flutter analyze` и затронутые `flutter test`.
  После backend-изменений: lint и профильные тесты; для правил — emulator gate.
- После завершённого среза — `loop-code-review`: устранить подтверждённые
  замечания и повторить нужные проверки. Числовая оценка сама по себе не закрывает задачу.
- Перед commit/push и деплоем проверяемого среза — полный `scripts/local_ci.sh`
  с сохранением результата для конкретного состояния кода. Любая последующая
  правка требует повторной соответствующей проверки. Физические device/sandbox
  сценарии объединены в финальном 02, до публикации релиза пользователям.
- Различать «кодовая часть завершена» и «подтверждено на устройствах».
  Отложенный device QA не блокирует следующую задачу разработки, но не считается пройденным.
- Для ускорения обязательны сравнимые измерения до/после на одном устройстве,
  режиме сборки и сценарии. Старый замер запуска около 10,9 с из марта 2026
  не считать текущим baseline.
- Отсутствие устройства или mobile-метрики фиксировать как «проверка отложена
  до 02» и продолжать доступную работу. Не подменять отсутствующий результат
  нулём, измерением desktop или отметкой «подтверждено на мобильном устройстве».
- При ухудшении call/auth/payment-корректности или согласованного бюджета
  откатить конкретный срез и сохранить диагностические материалы.

## 01 · Обязательный локальный release gate без GitHub Actions

**Статус: закрыто 07.09.2026.** `scripts/local_ci.sh` запускает единый набор проверок
через `scripts/local_ci_runner.js`. Лог и JSON-отчёт сохраняются в Git metadata;
отчёт содержит commit, dirty files, fingerprint, exit code и время. Успех
возможен только при зелёных проверках и неизменном содержимом входных файлов.
Ошибки, прерывание и запись журнала через workflow проверены отдельными тестами.
Финальный полный gate прошёл: `checksExitCode=0`, `inputsUnchanged=true`,
`exitCode=0`. Review loop принят без замечаний; реализация 10/10, тесты 9.5/10.
GitHub-enforced protection остаётся недоступной и не заявляется частью результата.

**Источник:** [P0-01](P0-01-ci-release-gate.md).
**Эффект:** защита от выпуска регрессий; прямого ускорения приложения нет.

Уже есть `.github/workflows/ci.yml` и `scripts/local_ci.sh`. При проверке
07.09 последний GitHub job не стартовал из-за billing-блокировки аккаунта;
у `main` не обнаружены branch protection и применимые rulesets.

Сделать:

1. Проверить и запускать существующий `scripts/local_ci.sh` на локальной машине:
   Flutter analyze/tests, backend lint/tests, security audit и Firestore emulator.
   Не создавать второй скрипт с расходящимся набором проверок.
2. Сохранять лог, exit code, commit и сведения о незакоммиченных изменениях.
   При сохранении через `tee` использовать `pipefail`, чтобы падение проверки
   не превратилось в успешный результат команды.
3. В рабочем процессе разрешать commit/push и деплой только после зелёного
   локального gate соответствующего состояния кода. Исправлять причину падения,
   не пропускать проверку ради выпуска.
4. Сохранить workflow для будущего восстановления. Не делать неработающий
   Actions-check обязательным условием merge и не требовать оплаты GitHub.

**Готово:** локальный gate воспроизводимо проходит, неуспех останавливает
процедуру выпуска, лог и проверенное состояние кода записаны в отчёте.
Это обязательное правило локального процесса, а не серверная защита GitHub:
другой участник с правом push технически может его обойти. Автоматическая
проверка каждого PR в GitHub остаётся отложенной, а не объявляется реализованной.

звонка. Кэш сбрасывается при уходе приложения в фон, защищён generation от

завершается fail-closed, но системные permission-dialog не имеют короткого

принят 9/10. Доказательства: [task07-call-permission-path-2026-09-08.md](../audit/performance_baselines/task07-call-permission-path-2026-09-08.md).
Фактический end-to-end выигрыш, регионы backend, orientation и first media
остаются до мобильного trace в 02; без него эти участки не менялись.

Сделать:

1. По замерам определить медленный этап: callable/Firestore, доставка,
   получение сессии, разрешения, credentials, навигация или Daily join.
2. Проверить повторные чтения сессии и конкурентные accept/navigation/join.

**Готово:** техническая задержка уменьшилась на одинаковом сценарии; нет
дублированных звонков, потери финальных субтитров, ложного trial consumption
