Дополнено 10.09.2026: промокод, детали/создание событий, перекрытия при скролле,

## Цель и границы

Показывать уже известный контент сразу, обновлять его в фоне и сохранять
позицию пользователя. Убрать временное имя «Собеседник», индикатор обновления
прогресса в профиле, скелетон событий и подпись «Проверяем участие».
Дополнение: согласовать язык уведомлений с языком приложения и исправить
позиционирование выпадающего меню службы поддержки.

Основание: шесть исходных скриншотов, два дополнительных скриншота профиля
(уведомление о копировании ID и меню поддержки) и статический разбор кода. На устройстве
сценарии в рамках этого исследования не воспроизводились; длительность задержек,
частота промахов кэша и изменение координат карточки пока не измерены. Отличия
масштаба/кадрирования скриншотов нельзя считать измерением layout shift.

## Выводы исследования

1. Flutter описывает чтение сохранённых данных с последующим обновлением из сети
   через repository/stream. Для нас это означает хранить последний отображённый
   результат независимо от текущего запроса. [Flutter offline-first](https://docs.flutter.dev/app-architecture/design-patterns/offline-first).
2. Firestore listeners сначала могут отдать локальный snapshot, затем серверный.
   `isFromCache` сообщает о происхождении данных, а не о необходимости скрыть их.
   Пустой локальный snapshot может быть неполным — нельзя сразу объявлять список
   окончательно пустым. [Firestore listeners](https://firebase.google.com/docs/firestore/query-data/listen),
   [offline cache](https://firebase.google.com/docs/firestore/manage-data/enable-offline).
3. На Apple/Android Firestore persistence включена по умолчанию. Но кэш SDK не
   заменяет синхронное начальное состояние виджета. В частности, новый завершённый
   Future может дать кадр `waiting`; `initialData`/сохранённая модель предотвращают
   замену контента лоадером. [FutureBuilder](https://api.flutter.dev/flutter/widgets/FutureBuilder-class.html).
4. Как пример реализации мессенджера, Stream Chat поддерживает локальное хранение
   каналов/сообщений. Это подтверждает полезность локальных данных, но не требует
   перехода нашего приложения на Stream, Drift или новую БД. Реализацию Telegram
   в этом исследовании не проверяли. [Stream Chat offline support](https://getstream.io/chat/docs/sdk/flutter/basics/offline-support/).
5. Для списков нужны стабильные ключи и соответствие ключа индексу при перестановках.
   Для сохранения scroll нужен живущий достаточно долго storage bucket или явное
   восстановление позиции. Один `PageStorageKey` внутри уничтоженного route не
   гарантирует восстановление. [ListView.builder](https://api.flutter.dev/flutter/widgets/ListView/ListView.builder.html),
   [PageStorage](https://api.flutter.dev/flutter/widgets/PageStorage-class.html).

Документация Flutter/Firebase дополнительно сверена через Context7. Рекомендации
ниже — адаптация к имеющимся компонентам, а не требование внедрить все примеры из
документации. Обновление Flutter/Firestore/go_router не входит в этот план.

## Что отложить

- Отдельную SQLite/Drift БД и полноценный offline sync engine — только если кэша
  Firestore и существующих bounded session caches недостаточно по измерениям.
- Перевод всех вкладок на `StatefulShellRoute.indexedStack` — возможен позже для
  сохранения отдельных navigation stacks, но потребует проверки auth/deep links,
  памяти и активных подписок. Сейчас достаточно сохранять данные и scroll вне
  пересоздаваемой страницы. [go_router StatefulShellRoute](https://pub.dev/documentation/go_router/latest/go_router/StatefulShellRoute-class.html).
- Полную замену пагинации сообщений на отдельный latest listener + исторические
  cursor pages — только при подтверждённой стоимости/задержке текущего растущего
  limit. Само по себе это не лечит смену имени. [Firestore cursors](https://firebase.google.com/docs/firestore/query-data/query-cursors).
- Полный redesign экранов, смену chat SDK и массовый рефакторинг god-components.

## Выпуск после реализации

Backend snapshot диалогов совместим со старым клиентом. Новый клиент обязан
работать и с legacy-документами без snapshot. Backfill выполнять отдельно после
dry-run и проверки количества документов; не запускать его в рамках планирования.
Версии приложения и backend, результаты проверок и ограничения зафиксировать
в итоговом release-отчёте. На текущем этапе код, production и деплой не менялись.
