# ТЗ: новая логика поиска и звонка

## Цель

В приложении должна появиться новая логика поиска собеседника для звонка. Студенты больше не должны становиться доступными пассивно через режим "Доступен сегодня". Вместо этого студент сам запускает активный поиск, попадает в очередь и соединяется с наиболее подходящим кандидатом из общего пула.

Общий пул кандидатов включает активных студентов и доступных учителей. Поиск не делится на последовательность "сначала студенты, потом учителя". Подбор выполняется равноценно по фильтрам, доступности и текущему состоянию пользователей.

## Фича 1. Удаление доступности у студентов

У студентов нужно убрать функционал "Доступен сегодня".

В студенческом интерфейсе не должно быть переключателя доступности, расписания доступности и логики, где студент считается доступным для звонка без активного поиска.

Студент может попасть в подбор только после нажатия кнопки "Начать поиск".

Поле и логика `availabilityToday` остаются актуальными только для учителей. Для студентов это поле не должно использоваться в подборе звонков.

## Фича 2. Кнопка "Начать поиск"

На студенческой стороне должна быть основная кнопка "Начать поиск".

После нажатия студент становится активным участником поиска. Кнопка меняется на "Остановить поиск". На экране отображается состояние ожидания пары.

Пока поиск активен, приложение должно показывать, что идет подбор собеседника. Студент может остановить поиск вручную.

Поиск автоматически завершается, когда:

- найдена и подтверждена пара для звонка;
- студент нажал "Остановить поиск";
- студент вышел из аккаунта;
- у студента закончился доступ к звонкам;
- студент уже находится в другом звонке;
- подходящая пара не найдена за 10 минут;
- заявка в очереди истекла по таймауту активности.

## Фича 3. Очередь активного поиска

После нажатия "Начать поиск" backend создает активную заявку поиска.

Заявка хранит:

- идентификатор студента;
- выбранный язык звонка;
- выбранные фильтры;
- статус поиска;
- время создания;
- время последней активности;
- состояние приложения: открыто или в фоне.

Клиент должен регулярно подтверждать активность поиска через heartbeat.

Heartbeat отправляется каждые 30 секунд.

Если приложение открыто, поиск работает до ручной отмены, найденной пары или истечения 10 минут без найденной пары.

Если приложение свернуто в фон, поиск остается активным максимум 10 минут.

Если приложение полностью закрыто и heartbeat не обновлялся 90 секунд, заявка считается неактивной и удаляется из поиска.

## Фича 4. Единый пул кандидатов

Поиск пары выполняется по единому пулу кандидатов.

В пул попадают:

- студенты, которые нажали "Начать поиск" и имеют активную заявку;
- учителя, которые доступны по своему расписанию.

Роль кандидата сама по себе не дает приоритета. Учитель и студент участвуют в подборе равноценно.

Кандидат должен пройти обязательные проверки:

- совпадает язык звонка;
- пользователь не находится в звонке;
- пользователь не заблокирован текущим студентом;
- текущий студент не заблокирован кандидатом;
- пользователь не нарушает правила повторного подбора;
- у пользователя есть право участвовать в звонке;
- для учителя подтвержден статус допуска;
- для учителя текущее время попадает в расписание доступности;
- у учителя есть активный VoIP/push токен для получения входящего звонка;
- для студента есть активная заявка поиска.

После обязательных проверок кандидаты сортируются по качеству совпадения:

1. точное совпадение уровня языка;
2. ближайший подходящий уровень языка на один шаг выше или ниже;
3. совпадение страны или города, если фильтр выбран;
4. более долгое ожидание в очереди;
5. стабильный технический порядок для одинаковых кандидатов.

Если выбран фильтр уровня, точное совпадение уровня важнее роли кандидата.

Если точного совпадения уровня нет, допускается кандидат с ближайшим уровнем на один шаг выше или ниже. Кандидаты с более дальним уровнем не используются для подбора по этому фильтру.

## Фича 5. Подбор студент-студент

Если лучшим кандидатом оказался другой активный студент, backend создает сессию звонка для двух студентов.

Обе заявки поиска переводятся в состояние найденной пары.

Если оба студента находятся в открытом приложении, оба автоматически переходят на страницу звонка.

Если один из студентов находится в фоне или на заблокированном экране, ему отправляется системный входящий звонок через VoIP/CallKit/ConnectionService.

Звонок стартует только после подтверждения входа обоими участниками.

Если фоновый студент принял входящий звонок, приложение открывается и переводит его на страницу звонка.

Если студент отклонил входящий звонок или не ответил за 45 секунд:

- созданная пара отменяется;
- неответивший студент удаляется из активной очереди;
- второй студент возвращается в активный поиск;
- backend продолжает подбор для второго студента по общему пулу кандидатов.

## Фича 6. Подбор студент-учитель

Если лучшим кандидатом оказался учитель, студент остается на экране ожидания соединения.

Учителю отправляется системный входящий звонок через VoIP/CallKit/ConnectionService.

Учитель может принять или отклонить звонок.

Если учитель принял звонок:

- backend подтверждает сессию;
- студент переводится на страницу звонка;
- учитель переводится на страницу звонка;
- оба участника помечаются как находящиеся в звонке.

Если учитель отклонил звонок или не ответил за 45 секунд:

- этот учитель исключается из текущей попытки подбора;
- студент остается в поиске;
- backend выбирает следующего лучшего кандидата из общего пула;
- роль следующего кандидата снова не имеет приоритета.

## Фича 7. Поведение при открытом приложении

Если приложение открыто и пара найдена, пользователь не должен вручную подтверждать переход на звонок.

Приложение автоматически открывает страницу звонка после серверного подтверждения пары.

На время между найденной парой и открытием звонка показывается состояние "Соединяем".

Если пара сорвалась до начала звонка, пользователь возвращается в состояние поиска.

## Фича 8. Поведение в фоне и при заблокированном экране

Если приложение свернуто или экран заблокирован, пользователь получает системный входящий звонок.

Системный входящий звонок должен содержать имя собеседника и указывать, что это звонок в приложении.

При принятии звонка приложение открывается и переводит пользователя на страницу звонка.

При отклонении звонка backend отменяет текущую пару и запускает дальнейшую обработку по правилам таймаута или отказа.

Если пользователь находится в фоне и поиск активен, заявка остается в очереди максимум 10 минут. После 10 минут фонового состояния поиск останавливается.

## Фича 9. Поведение при закрытом приложении

Если приложение полностью закрыто, активный поиск сохраняется только до истечения таймаута heartbeat.

Если пара найдена до истечения таймаута, пользователю отправляется системный входящий звонок.

Если пользователь не ответил на системный входящий звонок за 45 секунд, пара отменяется.

Если heartbeat истек до нахождения пары, заявка удаляется из очереди и пользователь больше не участвует в подборе.

## Фича 10. Таймауты

Для входящего звонка используется таймаут 45 секунд.

Если пользователь не ответил за 45 секунд, входящий звонок считается пропущенным.

Для полностью закрытого приложения и случаев потери активности используется таймаут 90 секунд без heartbeat.

Если поиск активен, но подходящая пара не найдена за 10 минут, поиск останавливается. Пользователь видит состояние "Пока никого не нашли" и может запустить поиск заново.

После подтверждения пары оба участника должны войти в комнату звонка за 60 секунд.

Если один из участников не вошел в комнату звонка за 60 секунд, пара отменяется. Участник, который вошел и ожидал второго, возвращается в активный поиск.

## Фича 11. Статусы поиска

У поиска должны быть следующие продуктовые состояния:

- поиск не запущен;
- идет поиск;
- пара найдена;
- соединение;
- звонок начался;
- поиск остановлен;
- пара не ответила;
- ошибка поиска.

Каждое состояние должно корректно отображаться в интерфейсе.

Пользователь не должен видеть технические статусы backend.

## Фича 12. Статусы сессии звонка

У сессии звонка должны быть следующие статусы:

- `searching` - идет поиск пары;
- `pending_confirmation` - пара найдена, ожидается подтверждение фонового участника или учителя;
- `connecting` - оба участника подтверждены, идет переход в звонок;
- `active` - звонок активен;
- `cancelled` - пара отменена до начала звонка;
- `expired` - истек таймаут ответа;
- `ended` - звонок завершен.

Статусы должны обновляться только через backend, чтобы исключить конфликт между двумя клиентами.

## Фича 13. Проверка доступа перед поиском

Перед запуском поиска приложение проверяет, что студент может начать звонок.

Проверяются:

- авторизация;
- подписка или другой активный доступ к звонкам;
- дневные или недельные лимиты;
- отсутствие активного звонка;
- доступ к камере и микрофону.

Если проверка не пройдена, поиск не запускается. Пользователь видит понятное состояние: оплатить доступ, исчерпан лимит, разрешить камеру и микрофон или завершить текущий звонок.

## Фича 14. Блокировки и повторный подбор

Подбор не должен соединять пользователей, если один из них заблокировал другого.

Подбор не должен повторять одну и ту же пару в рамках действующего правила защиты от повторов.

Если кандидат отклонил звонок или не ответил, он исключается из текущей попытки подбора.

Если пользователь сам отменил поиск, он удаляется из очереди и больше не участвует в текущем подборе.

## Фича 15. Восстановление состояния после перезапуска

При открытии приложения клиент проверяет активное состояние пользователя.

Если у пользователя есть активный поиск, интерфейс показывает экран поиска.

Если у пользователя есть сессия в статусе `pending_confirmation` или `connecting`, интерфейс открывает экран соединения или звонка.

Если у пользователя есть активный звонок, интерфейс открывает страницу звонка.

Если поиск или сессия уже истекли, интерфейс показывает обычное состояние без активного поиска.

## Фича 16. Завершение звонка

После завершения звонка оба участника удаляются из активного поиска.

Пользователи помечаются как не находящиеся в звонке.

После завершения открывается стандартный экран завершения или оценки звонка.

Повторный поиск начинается только после нового нажатия "Начать поиск".

## Фича 17. Ошибки и пустые состояния

Если нет подходящих кандидатов, поиск не должен завершаться сразу ошибкой. Пользователь остается в состоянии ожидания.

Если произошла техническая ошибка, пользователь видит понятное сообщение и кнопку повторного запуска поиска.

Если соединение сорвалось до начала звонка, пользователь возвращается в поиск.

Если пользователь потерял интернет, поиск останавливается после истечения heartbeat.

## Фича 18. Требования к интерфейсу

В студенческом интерфейсе должны быть состояния:

- кнопка "Начать поиск";
- кнопка "Остановить поиск";
- экран или блок "Ищем собеседника";
- состояние "Соединяем";
- состояние ошибки;
- состояние необходимости оплаты или доступа;
- состояние необходимости разрешить камеру и микрофон.

Интерфейс не должен показывать студенту расписание доступности.

Интерфейс учителя по расписанию доступности остается без изменений.

## Фича 19. Требования к backend

Backend должен быть главным источником истины для очереди, подбора, статусов сессии и таймаутов.

Backend должен атомарно создавать пару, чтобы один пользователь не мог попасть в два звонка одновременно.

Backend должен защищать подбор от гонок, когда несколько пользователей одновременно нажимают "Начать поиск".

Backend должен очищать истекшие заявки поиска и истекшие входящие звонки.

Backend должен продолжать подбор после отказа или таймаута кандидата.

## Фича 20. Прямой звонок конкретному учителю

Прямой звонок конкретному учителю из профиля остается отдельным сценарием.

Этот сценарий не является частью общей очереди поиска.

При прямом звонке студент выбирает конкретного учителя. Backend проверяет, что учитель доступен по расписанию, не находится в звонке, имеет активный VoIP/push токен, не заблокировал студента и соответствует базовым правилам доступа.

Если учитель доступен, ему отправляется системный входящий звонок.

Если учитель принял звонок, студент и учитель переходят на страницу звонка.

Если учитель отклонил звонок или не ответил за 45 секунд, прямой звонок завершается без автоматического перехода студента в общую очередь поиска.

Для запуска общего поиска студент должен отдельно нажать "Начать поиск".

## Фича 21. Критерии готовности

Функционал считается готовым, когда:

- у студентов полностью убрана пассивная доступность;
- студент может запустить и остановить поиск;
- активный студент попадает в очередь;
- поиск в открытом приложении работает до найденной пары, ручной отмены или 10 минут без пары;
- поиск в фоне автоматически останавливается через 10 минут;
- поиск в полностью закрытом приложении удаляется через 90 секунд без heartbeat;
- подбор работает по единому пулу студентов и учителей;
- роль кандидата не имеет приоритета перед фильтрами;
- фильтр уровня сначала ищет точное совпадение, затем ближайший уровень на один шаг выше или ниже;
- учителя без активного VoIP/push токена не попадают в подбор;
- два студента могут быть соединены в звонок;
- студент может быть соединен с учителем;
- прямой звонок конкретному учителю работает отдельно от общей очереди;
- foreground-сценарий открывает звонок автоматически;
- background-сценарий показывает системный входящий звонок;
- таймаут 45 секунд корректно отменяет неподтвержденную пару;
- таймаут 60 секунд корректно отменяет пару, если один из участников не вошел в комнату звонка;
- heartbeat корректно удаляет неактивные заявки;
- пользователь не попадает в два звонка одновременно;
- отмена, отказ и пропущенный звонок корректно возвращают второго участника в поиск;
- после завершения звонка пользователь не остается активным в очереди.
