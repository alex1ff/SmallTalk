# Единый каталог поддерживаемых локаций

## Цель

Во всех пользовательских сценариях заменить произвольный список стран и
городов четырьмя поддерживаемыми локациями:

1. `New York, US` — `US:new_york`;
2. `Bali, Indonesia` — `ID:bali`;
3. `Dubai, UAE` — `AE:dubai`;
4. `Phuket, Thailand` — `TH:phuket`.

Подписи одинаковы в русском и английском интерфейсе. Значение «Любая
локация» остаётся только в необязательном фильтре собеседника.

## Подход

Сохраняем совместимость с действующей схемой, но используем каноническую
идентичность `countryCode + cityKey`. Это минимально достаточный вариант:
существующие Firestore-поля и индексы продолжают работать, а город больше не
угадывается только по стране.

Канонический каталог событий становится источником разрешённых идентичностей.
Flutter-представление четырёх локаций использует те же пары и проверяется
контрактным тестом на полное совпадение. Серверный каталог генерируется из того
же JSON существующим генератором.

`CountryStruct` получает необязательный `cityKey`. Название структуры остаётся
legacy-именем ради совместимости, но новое значение считается корректной
локацией только при точном совпадении `code + cityKey` с каталогом. Новые UI и
бизнес-правила работают через отдельные функции каталога, а не через
произвольные `CountryStruct`.

## Данные и старые пользователи

- Новая локация пользователя сохраняется одновременно в `Country_NS` и
  `profileCity`.
- Предпочтительная локация собеседника сохраняется в
  `preferences.preferredLocation` с `code + cityKey`.
- Поисковый запрос передаёт оба поля: `countryCode` и `cityKey`.
- `matchProfile.city` синхронизируется из валидного `profileCity`.
- Публичная проекция публикует только валидную каноническую локацию.
- Старые `Country_NS`, `profileCity` и `preferredLocation`, отсутствующие в
  новом каталоге или не содержащие точную пару, логически считаются пустыми.
  Они не конвертируются автоматически: даже старый `US` не становится
  `New York`.
- При первом открытии соответствующего редактора пользователь должен выбрать
  новую локацию. Произвольное массовое удаление данных не выполняется.

Это даёт требуемый сброс без опасной миграции: старые значения сохраняются в
Firestore до следующего явного выбора, но не отображаются и не участвуют в
новой фильтрации.

## Поверхности интерфейса

Один и тот же порядок четырёх локаций используется в:

- студенческой регистрации;
- сохранённом/возобновлённом onboarding;
- редактировании профиля;
- фильтре собеседника на главной странице и в общем фильтре;
- создании и редактировании события;
- фильтре и выборе города на странице событий;
- связанных карточках и подписях выбранной локации.

Тексты «Страна», «Ваша страна», «Страна собеседника» заменяются на «Локация»,
«Ваша локация», «Локация собеседника» с соответствующими английскими строками.
Поиск внутри списка стран убирается: для четырёх пунктов он не нужен.

## События

`assets/jsons/events_city_catalog.json` сохраняет технические записи старых
городов только для чтения уже созданных событий. Пользовательская подвыборка
`supportedCities` содержит ровно четыре поддерживаемые локации. Для Bali
используется IANA-зона `Asia/Makassar`, для Phuket — `Asia/Bangkok`; New York и
Dubai сохраняют корректные существующие зоны.

Создание/редактирование события и серверные callable-функции принимают только
эти четыре пары. Существующие события в других городах не удаляются, но не
появляются в новых селекторах и не могут быть выбраны для нового или
отредактированного события.

## Matchmaking и защита границ

Клиент никогда не формирует location-фильтр из старого или неканонического
значения. `startSearch` валидирует присланную пару по серверному каталогу:

- оба поля отсутствуют — фильтр «Любая локация»;
- присутствуют оба и пара разрешена — точное совпадение города;
- передано одно поле, неизвестная пара или старое значение — запрос
  отклоняется как некорректный.

Кандидат соответствует фильтру только при наличии такой же валидной пары в
`profileCity`/`matchProfile.city`. Старый country-only профиль не проходит
фильтр конкретной локации.

## Ошибки и UX

- Старое/неизвестное значение отображается как «Локация не выбрана».
- Обязательные формы не отправляются без выбора одной из четырёх локаций.
- Необязательный фильтр собеседника позволяет очистить выбор до «Любая
  локация».
- Если каталог не загрузился, существующие стабильные loading/error состояния
  остаются; произвольный fallback на страну запрещён.

## Проверка

1. Каталог Flutter и серверный каталог содержат ровно четыре одинаковые пары
   в заданном порядке.
2. Старые country-only и старые city values считаются невыбранными.
3. Onboarding и профиль сохраняют канонические `Country_NS` и `profileCity`.
4. Dashboard/filters передают `countryCode + cityKey`; «Любая локация» не
   передаёт ни одного поля.
5. Event create/edit/list показывают только четыре локации; сервер отклоняет
   остальные пары.
6. Matchmaking принимает только канонический фильтр и требует точного города у
   кандидата.
7. Проверяются русские и английские подписи, узкие экраны и accessibility.
8. Запускаются `flutter analyze`, релевантные и полные Flutter-тесты, backend
   lint/test и генератор server catalog.

## Вне задачи

- геолокация устройства и автоматическое определение города;
- расстояние/радиус поиска;
- удаление исторических событий;
- массовая физическая очистка старых профилей;
- добавление новых локаций сверх четырёх.
