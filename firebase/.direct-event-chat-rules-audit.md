# Direct event chat Rules audit (untracked working note)

## Scope and codebase scan

- Scanned `lib`, `test`, and `firebase` Firestore references with `rg`; 2,043
  collection/query/path matches were reviewed as an inventory before changing
  the existing Rules file.
- Existing root Rules matches cover users, profiles, sessions, conversations,
  events and participants, event chats and messages, notifications,
  transactions, promo codes, reviews, packages, user learning data, event
  server-owned counters/requests/reports, and a default-deny fallback.
- This change is intentionally limited to
  `eventChats/{eventId}/messages/{clientMessageId}` create authorization. It
  does not alter existing read queries or any other collection's CRUD policy.

## Relevant assumed data model and access patterns

- `events/{eventId}`: server-owned event state. A writable chat requires
  `chatId == eventId`, `status == "active"`, and `canceledAt == null`.
- `eventChats/{eventId}`: server-owned exact metadata map containing
  `eventId`, `readAccessUserIds`, `createdAt`, and `updatedAt`.
- `events/{eventId}/participants/{uid}`: server-owned sender authority. The
  exact participant validator requires the canonical participant fields,
  matching `userId`, a valid role/status, timestamps, and active/left state.
- `eventChats/{eventId}/messages/{uuid}`: exact six-field direct-create shape:
  `senderId`, `senderDisplayName`, `senderPhotoUrl`, `text`, `createdAt`, and
  `deletedAt`.
- Flutter reads messages ordered by `createdAt` then document ID and limits
  pages. Existing bounded read/list Rules are unchanged.
- Cloud Functions/Admin SDK creates metadata, membership, callable messages,
  and tombstones; Admin SDK bypasses client Rules.

## Devil's advocate attacks

1. Public list exploit: blocked; event message reads still require an
   authorized active/frozen reader and bounded list query.
2. Unauthorized write: blocked for guest, nonparticipant, left participant,
   canceled event member, and admin-only identity.
3. Update bypass: blocked; message update is unconditionally false.
4. Ownership hijacking on create: blocked; `senderId == request.auth.uid` and
   sender presentation must equal the server-owned participant snapshot.
5. Ownership hijacking on update: blocked; update is false.
6. Immutable field modification: blocked; update is false and create requires
   `createdAt == request.time`.
7. Type juggling: blocked by exact types for IDs, presentation, text, and
   timestamp; nullable fields are explicitly constrained.
8. Create-vs-update validation bypass: blocked; update is false.
9. Resource exhaustion: blocked with 70-character name, 2,048-character photo,
   1,000-unit text limits, exact six fields, and UUID document IDs.
10. Required-field omission: blocked by `keys().hasAll(...)`.
11. Privilege escalation: blocked; an admin claim alone does not grant message
    create without an active participant document.
12. Schema pollution: blocked by `keys().hasOnly(...)`.
13. Invalid state transition: not applicable to immutable messages; event and
    participant state are read from server-owned documents.
14. Path traversal/scoping: blocked by fixed collection paths and lowercase
    UUID v4 message IDs; the payload contains no writable path field.
15. Timestamp manipulation: blocked by timestamp type and `request.time`
    equality, including denial of fixed, null, or missing client values.
16. Negative/overflow values: no numeric message fields exist.
17. Mixed-content leak: no email/phone/private participant fields are copied;
    only event-scoped display name/photo are denormalized to participant-only
    chat messages.
18. Counter replay: no counter mutation is part of the message create.
19. Orphaned subcollection access: blocked by required chat, event, and active
    participant parent documents with matching IDs/state.
20. Query mismatch: existing message read query policy is unchanged; direct
    create does not depend on a query predicate.
21. Validator pattern: create calls the dedicated exact-shape domain
    validator; update/delete are unconditionally false, so no update validator
    can be bypassed.

Batch attacks were also exercised: canonical creates may be batched, while a
spoofed/non-UUID create, overwrite, update, or delete makes the whole otherwise
allowed batch fail.

## Emulator-specific compatibility observation

The pinned Firestore emulator counts astral emoji as two units for
`String.size()`: 500 emoji satisfy the 1,000-unit direct limit and 501 do not.
This is fail-closed and does not weaken security. The approved client flow's
permission-denied callable fallback retains the product-level grapheme limit.
